# Migração v0.1.0 → v0.2 (release candidate)

Este documento registra cada mudança de contrato aplicada na reconciliação
v0.2 (Todo 5), com antes/depois e racional. A referência de mapeamento é
`mappings/v0.1.0-code-to-v0.2.md`; os achados de paridade vêm do harness do
Todo 4 (`scripts/check_contract_parity.py`, evidência em
`.omo/evidence/task-4-manifest.json`).

Superfícies de contrato cobertas: normativos (`docs/PIBRAS-STANDARD-v0.2-draft.md`,
`docs/PROPERTY-STANDARD-v0.1.md`), `schema/mbras.schema.json` (JSON Schema
2020-12), `types/mbras.ts` (Zod), `db/schema.sql` (DDL), OpenAPI, `samples/`,
`tests/golden/` e `portal-feed.valid.xml`.

## Mudanças breaking

### 1. `audit_log.change_type`: `TEXT` → enum `audit_change_type NOT NULL` (DDL)

Antes:

```sql
change_type   TEXT,                     -- insert | update | delete
```

Depois:

```sql
CREATE TYPE audit_change_type AS ENUM ('insert','update','delete');
-- ...
change_type   audit_change_type NOT NULL,
```

Racional: JSON Schema e Zod já restringiam `change_type` ao conjunto fechado
`insert | update | delete`; o DDL aceitava qualquer texto (inclusive NULL),
gerando drift de paridade. O enum + `NOT NULL` fecha o contrato nas três
superfícies. Breaking para escritores que gravavam valores fora do enum ou
NULL — esses valores nunca foram válidos nas demais superfícies.

### 2. `audit_log.trust_tier`: adicionada `CHECK (trust_tier BETWEEN 1 AND 6)` (DDL)

Antes:

```sql
trust_tier    SMALLINT,
```

Depois:

```sql
trust_tier    SMALLINT CHECK (trust_tier BETWEEN 1 AND 6),
```

Racional: o normativo e o Zod definem tiers de confiança 1–6; o DDL não
impunha o intervalo. Breaking apenas para linhas com valores fora de 1–6,
que já eram inválidas semanticamente.

## Mudanças aditivas / de conformidade

### 3. `ExposureRule.field_visibility`: `default: {}` (JSON Schema)

Antes:

```json
"additionalProperties": { "type": "string" }
```

Depois:

```json
"additionalProperties": { "type": "string" },
"default": {}
```

Racional: o Zod declara `.default({})`; o JSON Schema não documentava o
default, causando divergência de paridade. Aditivo — nenhum documento válido
passa a ser inválido.

### 4. Fixtures Zod: `z.record(z.unknown())` → `z.record(z.string(), z.unknown())`

Arquivos: `tests/contracts/aligned/contracts/types/mbras.ts`,
`tests/contracts/pre-reconciliation/contracts/types/mbras.ts`.

Racional: Zod v4 exige tipos de chave e valor explícitos em `z.record`;
a forma de 1 argumento falhava no `tsc --noEmit`. Sem mudança semântica
(chaves já eram strings).

harnesses — nenhum drift remanescente.
