# De/Para v0.1.0 técnica -> PIBRAS v0.2 draft

Este arquivo reconcilia os artefatos atuais com o alvo v0.2. A regra é evoluir sem quebrar consumidores existentes.

## Resumo

| Área | v0.1.0 técnica | v0.2 draft | Decisão |
|---|---|---|---|
| Código do imóvel | `property.code` | `external_ids[]` | Manter `code` como compatibilidade; adicionar `external_ids[]` como alvo. |
| Dinheiro | `Money { amount, currency }` | `Money { amount, currency }` | Preservar. `_brl` fica restrito a exportadores. |
| Identidade física | `Building -> Unit -> Property` | `Building -> Unit -> Property` | Preservar. Deduplicação ocorre em `Unit`. |
| Proprietários | `Owner` + `property_owners` | `Party` + `Ownership` | Adicionar alvo v0.2; manter compatibilidade. |
| Geografia | `Neighborhood` | `Geography` | `Geography` vira superset; `Neighborhood` permanece subtipo/compatibilidade. |
| Exposição | `ExposureRule` + `field_visibility` | `ExposurePolicy` | Adicionar política default-deny; mapear regras antigas. |
| Ingestão | `ingestion_record` + `pending_change` | `ImportSource` + `ImportBatch` + `ImportMapping` + trilha bruta | Manter trilha bruta; adicionar metadados de orquestração. |
| LGPD | campos em `Owner` e auditoria genérica | controller/processor + `DataSubjectRequest` | Adicionar entidades e campos mínimos. |
| Conformidade | exemplo único | `tests/golden/` | Adicionar fixtures positivas e negativas. |

## Identificadores externos

### Atual

```json
{
  "code": "MB18495",
  "provenance": {
    "source_system": "mbras_internal",
    "source_record_id": "MB18495"
  }
}
```

### Alvo

```json
{
  "code": "MB18495",
  "external_ids": [
    {
      "namespace": "mbras",
      "key": "property_code",
      "value": "MB18495"
    }
  ]
}
```

`code` permanece durante a janela de compatibilidade. Implementações novas devem preferir `external_ids[]`.

## Money

Campos como `asking_price_brl`, `minimum_price_brl`, `condominium_fee_brl` e `iptu_brl` não são canônicos.

### Canônico

```json
{
  "asking_price": {
    "amount": 1750000000,
    "currency": "BRL"
  }
}
```

## Unit como âncora de deduplicação

`Unit` deve receber metadados explícitos de dedupe:

```txt
dedupe_key
normalized_address_key
area_signature
duplicate_of_unit_id
dedupe_confidence
dedupe_review_state
```

Thresholds v0.2:

```txt
auto_match_threshold: >= 0.95
manual_review_band: >= 0.75 e < 0.95
confirmed_unique_threshold: < 0.75
```

### Compatibilidade de titulares: perfil de ensaio

A [norma v0.2, §5.6](../docs/PIBRAS-STANDARD-v0.2.md) distingue a pessoa do vínculo; a [RFC aceita](../docs/rfcs/accepted-001-v0.2-reconciliation.md) exige exatamente um alvo e no máximo 100% de participação ativa de proprietários por alvo. Não há conversão automática de todos os campos de uma representação para a outra.

| Entrada | Resultado esperado do ensaio |
|---|---|
| Antiga: Owner + Property.owners | Preservar UUID e campos comuns, inclusive endereço, contato, proveniência e auditoria. Criar vínculo no ciclo Property, sem atribuir a mesma participação a Unit. |
| Nova: Party + Ownership | Preservar os registros, inclusive vínculos exclusivos de Unit e metadados de privacidade de Party; não fabricar linhas antigas. |
| Mista, concordante | Reutilizar Party por UUID no mesmo escopo e vínculo inequívoco por (property_id, party_id). Preservar o ID canônico existente. Nunca parear por nome, contato ou documento fiscal. |
| Copropriedade | Uma linha por titular; preservar percentual (inclusive nulo/desconhecido), papel e indicador primário. 60 + 40 é válido; não completar uma participação ausente com o saldo. |
| Conflito de pessoa, vínculo, período ou proveniência | Rejeitar o lote sem sobrescrita. Divergências ou vários vínculos candidatos exigem revisão; não escolher o mais recente silenciosamente. |

**Inventário de consumidores.** JSON Schema e Zod ainda aceitam Owner e PropertyOwnerLink em Property.owners, além de Party e Ownership independentes. O exemplo `examples/property.sample.json` referencia o proprietário por ID, sem descrever a pessoa. Os três mapeadores de ingestão (CSV, Kenlo e ZAP) inicializam a lista vazia: ela não comprova ausência de titular. O arbitrador atua sobre Party; regras de autoridade também reconhecem Owner. Em SQL coexistem as quatro tabelas, com FKs separadas: gravar nas antigas não materializa as novas. A paridade de uma entidade isolada não prova que seus vínculos existem no banco.

**Execução e limites.** A [matriz compartilhada](../tests/golden/ownership-compatibility.json) contém só dados sintéticos. A [conversão de referência](ownership_compat.py) opera em memória sobre registros previamente validados e no mesmo escopo, não como migração de produção. Na raiz execute `python3 -m unittest discover -s tests/contracts -p test_ownership_compat.py`. O ensaio compara registros esperados, reprojeta as linhas de origem e repete a importação para verificar idempotência. Os links antigos são fornecidos com o ID da Property que os contém. Como não têm carimbo próprio, o ensaio usa a proveniência e a auditoria reais dessa Property e guarda a correspondência entre os vínculos em recibo separado. Não atribui evidência do Owner ao vínculo. UUIDv5 para um vínculo novo é convenção local reproduzível, não exigência do padrão.

**Perdas evitadas e decisões abertas.** `preferred_contact`, `marketing_consent` e `notes` não têm coluna equivalente em Party: ficam somente no recibo restrito do ensaio. A lista de campos presentes permite distinguir omissão de nulo ou default no retorno. O recibo também contém dados pessoais: não o publicar nem retê-lo fora da política aplicável. Não interpretar consentimento de marketing como base legal genérica. Regras universais de desempate, política de retenção do recibo, identificadores entre tenants, histórico com períodos conflitantes e migração SQL de metadados sem coluna equivalente exigem decisão explícita; não são resolvidas por este perfil.

## ExposureRule -> ExposurePolicy

| v0.1.0 | v0.2 |
|---|---|
| `exposure_level` | `exposure_policy.exposure_level` |
| `field_visibility` | regras `allow`/`deny` por campo |
| `allowed_channels` | `allowed_channels` |
| `requires_approval` | `requires_approval_for` |
| `price_display` | regra por campo `asking_price`/`display_price` |
| `address_display` | regra por campos `address.*` |

Semântica v0.2:

```txt
default deny para campos sensíveis, escrita, exportação e publicação;
deny explícito vence allow;
regra mais específica vence default;
needs_approval bloqueia envio até aprovação;
toda decisão retorna reason_code e applied_rule_ids.
```

## Ingestão

`ImportBatch` representa a operação de importação. `ingestion_record` continua guardando payload bruto. `pending_change` continua guardando diffs que precisam de revisão.

```txt
ImportBatch
  -> ingestion_record[]
  -> pending_change[]
  -> audit_log[]
```

## Critérios de aceite v0.2

Uma migração só está completa quando:

- o exemplo v0.1.0 ainda valida;
- pelo menos um exemplo v0.2 com `external_ids[]` valida;
- `ExposurePolicy` tem fixture default-deny;
- `DataSubjectRequest` tem fixture válida;
- `Unit` tem fixture de candidato de dedupe;
- README e VERSIONING apontam o status correto.
